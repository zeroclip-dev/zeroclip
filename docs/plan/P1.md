## Notes for this area

### Pitfalls

1. The Recorder can't be used as the Phase 1 sink. Recorder::new calls DvrBuffer::new (Phase 3 todo!, dvr.rs:88), and Recorder::push calls MasterClock::anchor/to_pts (Phase 2 todo!s, time.rs:166/187) and Tee::write (Phase 3, sink.rs:102). The actor.rs:214 comment ('Phase 1: create the Recorder') is wrong for now. Use the PacketCounter stand-in from P1.4.
2. SyntheticVideoSource::start is a Phase 3 todo! (synthetic.rs:85). Engine tests for Phase 1 need their own tiny FakeVideo.
3. Unfulfilled #[expect(dead_code)] attributes become errors under clippy -D warnings. Delete them in the same change that uses the field: crates/zc-video/src/capture.rs:55 and :57 (WgcCapture.pool/session, P1.7) and crates/zc-engine/src/actor.rs:103 (Msg::Health, P1.4). Not in scope: message_thread.rs:30, sink.rs:64, watchdog.rs:135/137, synthetic.rs:33/38.
4. windows-rs 0.62 Send-ness. All D3D11 interfaces (ID3D11Device, DeviceContext, Texture2D, VideoDevice, VideoContext, VideoProcessor*, Multithread) and the WGC classes (Direct3D11CaptureFramePool, CaptureFrame, GraphicsCaptureItem, GraphicsCaptureSession) are Send+Sync. The WinRT IDirect3DDevice wrapper and EVERY IMF* interface (IMFTransform, IMFSample, IMFDXGIDeviceManager, IMFSinkWriter, IMFActivate), plus ICodecAPI, are NOT Send. All MF objects therefore live on the one encoder thread. The FrameArrived handler re-creates IDirect3DDevice from the ID3D11Device when it needs Recreate.
5. TypedEventHandler::new takes Fn + Send + 'static, not FnMut. WgcCapture::start's FnMut on_frame needs a Mutex inside the handler. Never unwrap a poisoned lock on the capture thread.
6. ManuallyDrop fields leak COM references (VRAM) every frame unless released: D3D11_VIDEO_PROCESSOR_STREAM.pInputSurface (drop after VideoProcessorBlt) and MFT_OUTPUT_DATA_BUFFER.pSample/pEvents (take/drop after ProcessOutput).
7. MFTEnumEx/MFTEnum2 return a CoTaskMemAlloc'd array. Take each Option<IMFActivate>, then CoTaskMemFree, which needs the Win32_System_Com feature. ICodecAPI::SetValue/GetValue are cfg-gated on Win32_System_Com + Win32_System_Ole + Win32_System_Variant. VARIANT::from(u32) and From<bool> exist. None of these features is declared in zc-video yet. zc-video also lacks `tracing`, the app lacks `zc-video`, and `image` isn't a workspace dep (0.25.10 is already locked through eframe/arboard; use default-features = false, features = ["png"]).
8. zc-video declares Win32_Graphics_Direct3D10, but ID3D11Multithread (same IID as ID3D10Multithread, in the Direct3D11 module) makes it unnecessary. Remove it (CLAUDE rule 8).
9. An async MFT needs MF_TRANSFORM_ASYNC_UNLOCK set before any other IMFTransform call, otherwise MF_E_TRANSFORM_ASYNC_LOCKED. Don't call ProcessInput before METransformNeedInput or ProcessOutput before METransformHaveOutput. Send MFT_MESSAGE_NOTIFY_BEGIN_STREAMING and START_OF_STREAM or no NeedInput ever arrives. Handle MF_E_TRANSFORM_STREAM_CHANGE on the first output by re-setting the output type. Shut down with IMFShutdown::Shutdown / IMFActivate::ShutdownObject.
10. The scaffold API doesn't fit the async MFT. HwEncoder::encode(frame, pts, sink) assumes a synchronous transform; replace it with next_event/submit/take_output/drain (P1.10). ARCHITECTURE's thread table says the WGC thread 'submits to the encoder', but since IMFTransform isn't Send the WGC thread can only hand an NV12 ring slot to the encoder thread. Update the table.
11. WGC fires at the display refresh rate (144/240 Hz) and only when content changes. Decimate to fps (FramePacer, P1.3) or the real bitrate and GOP timing are wrong. A fully static screen produces no frames at all, which stretches GOPs and makes a screenshot time out. Acceptable for Phase 1; the Phase 3 DVR may want a repeat-last-frame ticker.
12. NV12 and the encoders need even width and height (round down with & !1). Hardware H.264 is often capped at 4096 px wide, so 5120×1440 super-ultrawide fails H.264 configuration; fall down the ladder or report Unsupported. Downscaling is out of scope.
13. Apartment::multithreaded() fails with RPC_E_CHANGED_MODE on an STA thread such as the eframe UI thread. Only the zc-video thread creates the Apartment and MF guards. WinRT activation elsewhere works through windows-core's implicit MTA fallback (CoIncrementMTAUsage).
14. In the spike, anyhow::Context and zc_win::error::WinResultExt both add `.context()` to Result. Importing both causes ambiguity errors, so use anyhow alone.
15. VideoStart had no capture_cursor although Settings and the UI have it (fixed in P1.4). VideoStart.codec isn't an Option, so the engine maps 'Auto' to Codec::LADDER[0] and lets Codec::select pick the best supported.
16. The status bar already shows the codec (src/ui/mod.rs:60); only EngineStatus.codec needs filling. The top bar says 'Buffering 0 s' while capturing until Phase 3 (P1.13 fixes the wording).
17. The engine health emitter posts to an unbounded std mpsc, which allocates in blocks. Per-frame FrameDelivered would allocate on the hot path, so report FrameDelivered only on the transition out of dropping (the Phase 4 watchdog only needs it to reset the drop count).
18. VideoSource::screenshot is synchronous. Mapping the staging texture and encoding the PNG happen on the engine thread; never block the WGC callback with Map. screenshot.rs's doc says 'on a background thread': update it.
19. GitHub windows-latest runners have no GPU. Don't write unit tests that create a D3D11 device or touch WGC/MF; test the pure helpers (fit_rect, gop_frames, bgra_to_rgba, FramePacer, video_start, file_stamp) and run the zc-video smoke example by hand. Examples are compiled by `cargo clippy --all-targets` and `cargo test`, so they must use tracing, not println (clippy print_stdout is on).
20. Docs and repo state disagree. CLAUDE.md and ARCHITECTURE.md describe .github/workflows/ci.yml, which doesn't exist (F.1). The spike has no README or notes; 'steps 1-4' are only main.rs doc comments. encoder.rs's probe doc promises a trial configuration, which this plan moves into HwEncoder::new plus Codec::step_down. DESIGN §3 and backoff.rs describe DXGI_ERROR_ACCESS_DENIED from WGC (see Q2).
21. zc-win needs no Phase 1 changes. clock/com/mf/error are done; drive.rs is a Phase 3 todo! (drive.rs:17) and message_thread.rs is Phase 2. Don't touch either.
22. Every COM/Win32 call is unsafe in windows-rs 0.62. Each unsafe block needs a `// SAFETY:` comment (clippy undocumented_unsafe_blocks), and unsafe_op_in_unsafe_fn is deny, so the EnumDisplayMonitors callback body needs its own unsafe block. Public items in zc-video need docs (missing_docs = warn becomes an error in CI).
23. MF_MT_FRAME_SIZE and MF_MT_FRAME_RATE are packed u64s: (width << 32) | height and (num << 32) | den. Colour tags on the encoder output type (BT.709, 16-235) must match the video processor's output colour space, or colours shift slightly.
24. The 8-slot NV12 ring reuses pre-created IMFSamples without release tracking. If an encoder ever holds more than ~6 inputs, a texture could be overwritten while still queued. Upgrade path: MFCreateTrackedSample (marked with a ponytail: comment).

### Open questions, as the inventory saw them

Where this disagrees with [README § Decisions](README.md#decisions), the README wins.

Q2, the HDCP resume signal (decide by Phase 1). What the code and docs assume today: DESIGN §3, crates/zc-core/src/backoff.rs and the capture.rs plan item 6 all say WGC fails with DXGI_ERROR_ACCESS_DENIED while protected content is on screen, and that capture should retry on Backoff::hdcp() (250 ms doubling to 5 s) and emit placeholder frames. That is Desktop Duplication behaviour. WGC is expected to keep delivering frames with the DRM surface composited black and no error, and it has no event for protected-content transitions: GraphicsCaptureItem only exposes Closed. Recommendation: (1) implement the Backoff spec (P1.2). (2) Classify DXGI_ERROR_ACCESS_DENIED and E_ACCESSDENIED as SourceError::Protected, but only on the capture path (capture.rs helper; not zc-win's generic platform_error, where E_ACCESSDENIED means other things). (3) Restart capture with backoff only when a capture call actually fails that way. (4) Skip synthetic placeholder frames in Phase 1. (5) Verify with a Netflix tab in P1.15 and record D18. Why: it costs a few lines, works whichever behaviour the hardware shows, and avoids building a placeholder-frame generator for a failure WGC probably never raises. If hardware shows frames stop entirely during DRM, a repeat-last-frame ticker becomes a Phase 3 item, since the GOP-indexed buffer needs time-regular keyframes.

Q8, multi-monitor and HDR (decide by Phase 1–2). What the code assumes: CaptureTarget defaults to PrimaryMonitor; Monitor(i) and Window(hwnd) variants exist but nothing selects them; capture uses DirectXPixelFormat::B8G8R8A8UIntNormalized (SDR). Recommendation for v0.1: capture the primary monitor only, in BGRA8, and let DWM do the HDR-to-SDR conversion; no tone mapping of our own. Fix the encode size at capture start, rounded to even, and letterbox later sizes in the video processor (P1.8) so a resolution change never restarts the encoder or the stream. Defer follow-the-game monitor selection to the Phase 4 profile engine, which already learns the game window (MonitorFromWindow, then restart capture between GOPs). Defer real HDR (R16G16B16A16Float plus a 10-bit HEVC/AV1 profile) past v0.1. Why: keeping one size and one colour pipeline per session matters for containers and concat (DESIGN §9 codec/resolution mismatch), and HDR roughly doubles the conversion work. Record it in DECISIONS (next free D-number) in P1.15 and keep a narrowed Q8.

Q3, fMP4 vs MKV (Phase 3; touched only indirectly). MF H.264/HEVC encoders emit Annex-B access units, and both fMP4 (avcC/hvcC) and MKV (CodecPrivate) need the parameter sets out of band. The VideoSource port currently returns only the Codec. Phase 3 will need the encoder's MF_MT_MPEG_SEQUENCE_HEADER plus the encode size and fps, for zc_mux::container::TrackInfo. Recommendation: don't add a port for it in Phase 1 (YAGNI). The Phase 3 author extends VideoSource::start's return value (e.g. a VideoStarted { codec, size, fps, codec_private }) when the muxer lands. Phase 1 should still read the output type after the first MF_E_TRANSFORM_STREAM_CHANGE so the code path is known to work.

Other questions (Q1, Q4–Q7, Q9, Q10) are outside this area.

### P1.3 · zc-core: FramePacer, which thins WGC's refresh-rate frame stream down to the target fps

Size **S** · no hardware needed · depends on P0.4

**Finding from the Phase 0 spike (2026-10-04), static screens:** WGC only delivers a frame when something on screen changes. On a quiet desktop the spike got long stretches with no frames at all (up to 1.1 s; 373 frames in 10 s, and VLC showed 36.9 fps). The encoder dropped nothing: frames written matched frames in the file exactly at both 20 and 60 Mbps. The result is a variable-frame-rate file, which plays fine, but it matters for ZeroClip: keyframes are timed by frames, so a static screen can stretch a GOP far beyond 1–2 s, and the DVR evicts by GOP (D5). Give `FramePacer` a second job: if no frame arrives within one period, report that a repeat is due, so the source can re-submit the last converted frame and keep the stream at the target fps. Add specs for both behaviours.

**Finding from the Phase 0 spike (2026-10-04):** WGC's default minimum gap between frames is about 16.7 ms. On a 200 Hz display that lands on every 4th refresh and gives only 50 fps, below a 60 fps target. P1.7 therefore lowers the minimum interval, so WGC delivers every refresh, and this `FramePacer` does the decimation to exactly the target fps. Test it with a 200 Hz arrival cadence (5 ms) and a 60 Hz one (16.7 ms), and make sure a 60 fps target on a 200 Hz source still yields 60 fps, not 50.

**Files:**
- `crates/zc-core/src/time.rs`
- `crates/zc-core/src/lib.rs`

**Reuse:**
- Hns (crates/zc-core/src/time.rs)

**Steps**

Why: WGC fires FrameArrived at the display refresh rate (144/240 Hz) whenever content changes. The encoder is configured for `fps` with GOP = fps × interval frames. Feeding it 144 fps would multiply the real bitrate by 2.4 and shrink GOPs to 0.4 s. Pure logic, so it goes in zc-core with tests (ARCHITECTURE 'Where does this go').
1. Add to time.rs:
```rust
/// Keeps at most `fps` frames per second from a capture stream (DESIGN §3).
#[derive(Clone, Copy, Debug)]
pub struct FramePacer { interval: Hns, next_due: Option<Hns> }
impl FramePacer {
  #[must_use] pub fn new(fps: u32) -> Self { Self { interval: Hns(Hns::PER_SECOND / i64::from(fps.max(1))), next_due: None } }
  #[must_use] pub fn interval(&self) -> Hns { self.interval }
  /// Whether to encode a frame captured at `t`. Frames up to a quarter interval early count as on time, so jittery 60 Hz input at 60 fps isn't thinned.
  pub fn accept(&mut self, t: Hns) -> bool {
    let slack = Hns(self.interval.ticks() / 4);
    if let Some(due) = self.next_due && t + slack < due { return false; }
    let due = self.next_due.unwrap_or(t);
    // Stay on the frame grid, but after a pause restart from `t` instead of bursting to catch up.
    self.next_due = Some(if t - due >= self.interval { t + self.interval } else { due + self.interval });
    true
  }
}
```
   The quarter-interval slack is a tuning knob. Keep it as a named const.
2. Tests in time.rs: (a) 144 Hz input (t_k = k*10_000_000/144) for 1 s at fps 60 keeps 59..=61 frames; (b) 60 Hz input with ±1 ms jitter at fps 60 keeps every frame; (c) 30 Hz input at fps 60 keeps every frame (it never duplicates); (d) after a 1 s gap the next frame is accepted and the one after that only one interval later (no burst).
3. Update the `time` row in lib.rs's module table to mention the frame pacer.

**Verify**

cargo test -p zc-core frame_pacer; cargo clippy --workspace --all-targets -- -D warnings
