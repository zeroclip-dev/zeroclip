## Notes for this area

### Pitfalls

Cross-phase dependencies:
- P4.3's step-down specs panic until Codec::step_down (media.rs:41, Phase 1) is implemented. P6.10 needs Backoff (backoff.rs:45/50, Phase 1) and WritePacer::delay (pacing.rs:68, Phase 3).
- P4.6, P4.7, P4.9 and P4.11 need Phase 3's real DvrBuffer, Recorder, SaveClip dump path, session recording and SyntheticVideoSource start/stop.
- P4.10 needs Phase 2's RawInputSource::start.
- Pure tasks have no upstream dependency and could be pulled forward: P4.1-P4.5, P5.2-P5.7, P6.1-P6.5, P6.8. CLAUDE.md says to stay in the current phase, so ask 0xtikaa first.

Engine pitfalls:
- actor.rs publish_status() currently overwrites status.buffer_window with the default profile on every publish. It must use the active clamped window, or the profile engine looks broken.
- status.game currently holds the full exe path; change it to the file name.
- Sticky profiles are essential. If unknown foreground apps (Discord, Task Manager) fell back to the default profile, killing the game from Task Manager would shrink the buffer from 2 min to 1 min before the rescue dump, destroying exactly the footage crash rescue exists for.
- Synthetic source:
  - Preserve SyntheticStream and FaultPlan across stop/start (return them from the worker's JoinHandle).
  - Consume encoder_fault_at with take(); otherwise the restarted source faults at frame 300 forever.
  - In non-realtime mode: yield_now() each frame, because the tight push loop can starve the engine on the recorder mutex.
  - Don't emit FrameDelivered per frame there; the engine inbox is an unbounded mpsc channel.
- The synthetic_harness watchdog spec comment says "a clip saved afterwards still contains the frames from before the fault". That contradicts DESIGN §8 (the buffer restarts empty at RESUMING; pre-fault footage is flushed to its own file). Change the comment and assertion deliberately and explain why in the commit, per CLAUDE.md.
- Don't call video.start()/stop() while holding the recorder lock; resize/clear take it briefly themselves.

Crash rescue:
- Task Manager's Processes-tab "End task" may close a game gracefully (WM_CLOSE gives exit code 0), which is treated as a clean exit and gives no prompt. The Details tab's End task and taskkill /F give exit code 1. Use those for the done-when test.
- HANDLE is !Send in windows-rs 0.62: move the raw value into the watcher thread.
- Only call GetExitCodeProcess after the wait; before exit it returns STILL_ACTIVE (259).

zc-store:
- StoreError is hand-rolled; CONTRIBUTING.md rule 5 requires thiserror, so replace it.
- PRAGMA foreign_keys is off per connection by default, so the schema's ON DELETE CASCADE silently does nothing unless it is enabled.
- Set journal_mode=WAL with pragma_update_and_check, because the pragma returns a row.
- rusqlite::Connection is Send but not Sync: share it as Arc<Mutex<Store>> and never hold it across an ffmpeg run.
- Never edit migrations/0001_init.sql; add 0002_*.sql instead.

eframe 0.36 / tray:
- eframe always shows the root window after the first painted frame (epi_integration.rs post_rendering), so ViewportBuilder::with_visible(false) can't start hidden. Send ViewportCommand::Visible(false) from logic() until ViewportInfo::visible() is Some(false).
- A hidden root viewport still gets App::logic calls on request_repaint, because eframe paints invisible windows directly (egui#5229 fix). Move engine and tray draining from ui() into logic(); ui() doesn't run while hidden.
- tray-icon must be created on the main thread inside the running event loop (the CreationContext closure) and kept alive in the app struct.

ffmpeg:
- Release builds are windows_subsystem="windows", so every ffmpeg/ffprobe spawn needs CommandExt::creation_flags(0x08000000 CREATE_NO_WINDOW), or a console flashes.
- Use -nostdin, or ffmpeg can block waiting on stdin.
- Use -n so exports never overwrite.
- The scaffold's `-to` before `-i` is version-sensitive; use `-t <duration>` after -i.
- ffprobe pts_time is absolute, so subtract format start_time before snapping (-ss is relative to the file start).
- HEVC in MP4 gets the hev1 tag by default; Safari/QuickTime need -tag:v hvc1, but only add it for HEVC (it breaks H.264).
- Escape `'` as `'\''` in concat lists, and use -safe 0 for absolute paths.

Secrets:
- Settings derives Debug, and the engine logs every inbox message at trace (`tracing::trace!(?msg)`, which includes ApplySettings). Webhook URLs and client secrets in plain Strings would land in log files and the flight recorder, so use a Secret newtype with redacted Debug.
- DiscordWebhook derives Debug and prints the full webhook URL (a credential); replace it with a manual impl.
- The YouTube refresh token should be stored with DPAPI (zc-win), not in settings.toml.

HTTP:
- Prefer reqwest with default-features=false + native-tls (SChannel). rustls' default aws-lc backend needs CMake/NASM to build on Windows and CI.
- The resumable upload's 308 "Resume Incomplete" is not a redirect: build the client with redirect::Policy::none().
- Registry stores Box<dyn Destination>, but upload tasks on tokio need 'static, so switch to Arc.
- Google OAuth consent screens in "Testing" status expire refresh tokens after 7 days, which looks like AuthState::Expired weekly.

Flight recorder:
- It sees only what the global EnvFilter lets through.
- It allocates per event, so hot-path threads must log only at trace.
- The panic hook must use try_lock, to avoid a deadlock if the panic happened inside on_event.

Docs vs code:
- DESIGN §7 says profiles are looked up in SQLite, but they live in settings.toml (see the open-questions note).
- DESIGN §8 says "recovery.tmp"; the plan uses recovery-<unix>.<ext>.tmp so a second crash never overwrites an unanswered rescue. Update DESIGN §8.
- The ARCHITECTURE Threads table says the tokio pool handles waveform/ffmpeg jobs from Phase 5; the plan uses plain std threads there and introduces tokio only for uploads in Phase 6. Update the table.
- DESIGN §10 says the Discord free cap is "20 MB" while the code uses 20 MiB (Discord's limits are effectively MiB).
- CLAUDE.md mentions .github/workflows/ci.yml, but it doesn't exist yet. The ROADMAP Foundations box is unchecked, and the CI badge (X.3) depends on it.

### Open questions, as the inventory saw them

Where this disagrees with [README § Decisions](README.md#decisions), the README wins.

Q3 (fMP4 vs MKV, Phase 3, touched by P4.11/P5.x): crash rescue writes with settings.recording.container and stores the extension in the file name (recovery-<unix>.<ext>.tmp), so either works. The editor always exports .mp4 with +faststart, so the shareable output is the same either way. Leaning fMP4 makes P5.12's "plays in a browser" check trivial.

Q4 (snapshot copies, Phase 3, touched by P4.9/P4.11): the crash rescue and watchdog flush both call DvrBuffer::snapshot. That allocates and copies the whole window (~750 MB for 5 min) at the worst moment, on top of the page-locked ring. Copy-out is acceptable for Phase 4 because neither path is the hot path. Note the memory spike in the P4.17 manual test (Task Manager commit size). If it hurts, a segment-sharing design (Q4's alternative) fixes it.

Q5 (DVR + session at the same time, Phase 3, touched by P4.7): the code assumes both (the Tee). P4.7 starts a session from a profile while the DVR keeps running. If Phase 3 chose exclusive, P4.7 must stop the DVR during a session, and crash rescue for session-profile games then relies only on the fragmented file.

Q6 (buffer resize under load, Phase 4, P4.6): the code says the engine "pauses the writer around this call" (DvrBuffer::resize docs), and DESIGN §7 says "brief writer pause". Recommendation: a brief writer pause, i.e. Recorder::resize runs DvrBuffer::resize under the recorder mutex, with a tracing line timing it. Why: it is the simplest option and needs no second allocation. Resizes only happen when the tracked game changes, because profiles are sticky (unknown apps never trigger one). The real limit is the watchdog: 10 dropped frames at 60 fps is 166 ms. If the logged pause gets near ~100 ms (for example growing to 5 min with VirtualLock), move the allocation and page-locking out of the lock (allocate first, then swap). Record this as a DECISIONS entry and remove Q6.

Q7 (playback, Phase 5; settled in planning as D22, keyframe thumbnails + external player): the code assumes nothing yet. Recommendation: an external player. "Preview selection" runs ffplay -ss <in> -t <len> (it ships next to ffmpeg.exe), with the default player as a fallback. Why: egui_video links FFmpeg via ffmpeg-next, which breaks D3 (FFmpeg is a process, not a library: licensing and build complexity). libmpv is a heavy DLL that changes the installer (DESIGN §2). The editor's value is instant stream-copy cuts with visible snap points, and that needs no embedded decoder. Confirm with 0xtikaa before writing it into DECISIONS.

Q9 (YouTube audit, Phase 6, P6.0, P6.9-P6.11): DESIGN/D14 assume bring-your-own credentials make YouTube usable while the audit is pending. Google's videos.insert docs restrict uploads from every unverified API project created after 28 Jul 2020 to private, and a user's freshly made BYO project is exactly that. So BYO likely fixes quota but not unlisted visibility. Recommendation: test this in 15 minutes at the start of Phase 6 (P6.0) before building OAuth and the upload. If uploads are locked private, either ship YouTube as "private upload to your channel" (cloud archive; honest UI text) or gate it on the audit. Discord (D14) stays the default destination either way.

Q10 (Discord size limit, Phase 6, P6.4): the code starts from ASSUMED_LIMIT_BYTES = 20 MiB and lowers it on 413. Recommendation: keep it learn-only. A webhook cannot read the guild's boost tier or the user's Nitro status without a bot token, and the 413 body carries no limit. On a 413, step down to the next known tier (500/100/50/25/20/10/8 MiB) below the rejected size. Keep the learned value in memory per run. Add a manual "limit override" setting only if users with boosted servers ask, since starting at 20 MiB under-serves them. Move to DECISIONS when P6.4 lands.

Q1 (loopback include mode, Phase 2) is touched only through AudioSource::set_target_process: P4.6 calls it with the tracked game's pid, and P4.7 calls it with None when the game exits. Sticky profiles mean audio keeps following the game while the user alt-tabs, which is what include mode needs.

Also a design point not in the Q-list: DESIGN §7 says the profile is looked up "in SQLite", but profiles live in settings.toml (ProfileSet in Settings), and the zc-store crate doc says "once they outgrow the settings file". Recommendation: keep them in settings for Phase 4 and leave the game_profiles table unused. Say so in a DECISIONS entry so nobody migrates them by accident.
