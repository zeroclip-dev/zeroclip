## Notes for this area

### Pitfalls

1. Cross-phase ordering trap.
- `Recorder::new` calls `DvrBuffer::new`, which is `todo!` today. `Recorder::push` calls `MasterClock::to_pts`, which is a Phase 2 `todo!`.
- If the Phase 1 plan wires GpuVideoSource into the actor through the Recorder (as the comment in actor.rs suggests), it will panic at startup.
- P3.1 to P3.5 are pure zc-core and can be pulled ahead of Phase 1 wiring. Otherwise Phase 1 must use a throwaway counting sink.

2. Tee writers are on the hot path.
- `PacketWriter::write` runs on encoder and audio threads under the recorder mutex, so it may not touch the file system or allocate.
- So a session writer cannot be `ChunkedWriter<File>` directly. Use the spool plus IO thread (P3.21). ChunkedWriter, PacedWriter and the fMP4 writer are IO-thread-only.

3. The `ContainerWriter::flush_fragment` doc overstates durability.
- It claims everything written so far plays if the process dies. A ChunkedWriter below it holds up to one chunk (16 MiB) in RAM.
- A game crash loses nothing, since ZeroClip is a separate process. A ZeroClip crash loses at most one chunk. Fix the doc (P3.11).

4. Port gap.
- `container::create` needs codec, width, height and codec_private. `VideoSource::start` returns only `Codec`, and `TrackInfo` lives in zc-mux, which adapters may not depend on.
- P3.8 moves TrackInfo and TrackKind into zc_core::media (re-exported from zc_mux::container) and adds a required `VideoSource::format()`.
- Audio needs no port change: the engine knows AudioStart, and the muxer synthesizes the AAC-LC AudioSpecificConfig. Never pass the MF AAC `MF_MT_USER_DATA` blob raw: it begins with 12 bytes of HEAACWAVEINFO.

5. Codec configuration from hardware MFTs.
- `MF_MT_MPEG_SEQUENCE_HEADER` is often only populated after the first ProcessOutput.
- The plan therefore takes parameter sets from the first IDR in-band, which most hardware H.264 and HEVC MFTs repeat on every IDR, with the MF attribute as a fallback.
- What MF's AV1 encoder puts in that attribute is unverified. Check on hardware in P3.27.

6. MP4 samples need 4-byte length-prefixed NALs, not Annex-B start codes. HEVC SPS profile_tier_level almost always contains emulation-prevention bytes (00 00 03), so unescape before copying into hvcC. AV1 temporal-delimiter OBUs should be dropped from samples.

7. WGC is variable frame rate, since it only delivers frames when the screen changes. fMP4 sample durations must come from PTS deltas, not from `PacketMeta.duration`, or video drifts against audio. Each fragment's tfdt resets to the true pts.

8. Two audio tracks: browsers and Discord play only the first. Declare game audio first. The mic is audible only in VLC or after a Phase 5 export that mixes it (amix, re-encoding audio only). Put this in the README's known limits.

9. windows-rs 0.62 features:
- `CreateFileW` is gated on `Win32_Security`, which zc-win does not declare.
- `VirtualLock` needs `Win32_System_Memory`, which is not declared.
- Already declared:
  - `GetCurrentProcess`, `Get/SetProcessWorkingSetSize`: Win32_System_Threading.
  - `DeviceIoControl`: Win32_System_IO.
  - `IOCTL_STORAGE_QUERY_PROPERTY`, `STORAGE_PROPERTY_QUERY`, `DEVICE_SEEK_PENALTY_DESCRIPTOR`, `StorageDeviceSeekPenaltyProperty`, `PropertyStandardQuery`: Win32_System_Ioctl.
  - `GetVolumePathNameW`, `GetVolumeNameForVolumeMountPointW`: Win32_Storage_FileSystem.
- `HSTRING: From<&Path>` exists in windows-strings 0.5, and `windows::core::Owned<HANDLE>` closes the handle on drop.
- Open the volume GUID path *without* its trailing backslash, or you get the root directory instead of the volume device. That route also handles folder mount points, which the hinted `\\.\X:` route does not.

10. VirtualLock fails beyond the process's minimum working set (about 200 KB by default) with ERROR_WORKING_SET_QUOTA, so raise it with SetProcessWorkingSetSize first. `vec![0; n]` is calloc'd and lazily committed; VirtualLock commits it, which is the intent. The DVR rings are large allocations that HeapAlloc serves with VirtualAlloc, so freeing them releases the lock. Phase 4's resize must re-lock.

11. DvrConfig cannot gain fields: the specs build it with struct literals. That is why the index capacity per ring is derived from byte sizes (1 entry per KiB for video, per 128 B for audio, at least 1024).

12. Debug: DvrBuffer derives Debug, so PacketRing must implement Debug by hand, or printing a buffer dumps hundreds of MB.

13. Unbounded `std::sync::mpsc` allocates a block about every 31 sends. Health events sent per frame through `Emit` on encoder threads would allocate on the hot path and flood the actor. Send only state changes (drops, faults, and the first delivered frame after a drop run) — also relevant to the Phase 1 and Phase 4 plans.

14. Settings allow a 1800 s buffer at 100 Mbps (22.5 GB). Without `clamp_window` (pulled forward as P3.16), `DvrBuffer::new` aborts the process on allocation failure.

15. Scaffolding that becomes dead in this phase:
- The actor test `unbuilt_features_say_which_phase_delivers_them` asserts SaveClip gives NotImplemented { phase: 3 }.
- Once no command calls `Actor::not_implemented`, that helper is dead code and `-D warnings` fails. Delete the helper and the test.
- Expect attributes to delete: sink.rs:64 (`next_id`), synthetic.rs:33 and :38, actor.rs:103 (`Msg::Health`) if Phase 1 has not already.

16. Synthetic payloads are not real H.264. Synthetic clip files are structurally valid MP4 but do not decode, and the harness spec only checks existence and duration. Decodability can be proven only with P3.14's x264 example (needs ffmpeg) or on hardware (P3.27).

17. File names need local time.
- The `time` crate is already in Cargo.lock through tracing-appender. Enable `formatting`, `local-offset` and `macros` instead of adding chrono.
- `now_local()` can fail on Unix in multithreaded processes, so fall back to UTC.
- Use `File::create_new` with ' (2)' suffixes so a clip is never overwritten. Avoid ':' in names.

18. Single IO thread versus several: ARCHITECTURE describes one IO thread. A paced 750 MB HDD dump at 40 MB/s takes about 19 s, which would overflow a recording's 32 MiB spool if they shared a thread. The plan uses one thread per dump or recording; update ARCHITECTURE.

19. The std library cannot lower thread priority. The 'low-priority IO thread' (DESIGN section 4) would need Windows APIs (`THREAD_MODE_BACKGROUND_BEGIN`). Pacing is the mitigation for v0.1.

20. File preallocation and the same-drive warning are deferred.
- DESIGN section 4's `SetEndOfFile` preallocation would leave a zero-filled tail that breaks truncation-playability in fMP4. The right API is `SetFileInformationByHandle(FileAllocationInfo)`, which reserves space without moving EOF. Not in the Phase 3 checklist; deferred.
- The 'same spindle as the game' warning needs the game's exe path and IOCTL_STORAGE_GET_DEVICE_NUMBER. Deferred to Phase 4.

21. The CI workflow does not exist yet (`.github/` is absent, and the Foundations box is unchecked). It is needed before tagging v0.1 or adding a badge.

22. CLAUDE.md still says 'Current phase: Phase 0'; update it as phases land.

23. No mfra index: fragmented files without mfra or sidx may show no duration or seek poorly in Chrome. VLC and ffmpeg are fine. Add mfra/tfra in `finish()` only if P3.27 shows the problem.

24. Synthetic source restarts: return the SyntheticStream from the worker thread on join. Otherwise a stop and restart (Phase 4 watchdog) resets PTS to 0, which a real QPC clock never does.

25. Cargo test realities: every engine test now allocates a default 155 MB DVR. That is calloc'd, so it is cheap and only lazily committed, and Ports.lock_memory is None in tests, so nothing locks it.

### Open questions, as the inventory saw them

Where this disagrees with [README § Decisions](README.md#decisions), the README wins.

Q3, fMP4 or MKV.
- What the code assumes now: `ContainerFormat::default()` is FragmentedMp4 (crates/zc-core/src/media.rs). The settings UI offers both. DESIGN section 11 says Phase 3 builds a "direct-to-disk fMP4 writer". The ContainerWriter trait writes over a plain `io::Write` with no Seek.
- Recommendation: fMP4 only. `create(Matroska, ..)` returns Unsupported, and the variant stays so old settings files still parse.
- Why:
  (a) Discord is the primary destination (D14). fMP4 clips play inline there and in browsers with no remux. MKV clips never would.
  (b) Both formats can be written without seeking: fMP4 puts moov up front with mvex, then moof+mdat per GOP. Both stay playable after truncation at a fragment boundary.
  (c) The hard part is identical for both: avcC, hvcC, av1C, the AAC config, and converting Annex-B to length-prefixed NALs. P3.9, P3.12 and P3.13 do it once in a container-agnostic `bitstream` module. MKV's only real gain is simpler EBML framing.
  (d) It matches the existing default and DESIGN.
- Cost: about 300 more lines of box boilerplate than EBML. Clips may need an mfra index for good browser seeking (contingency in P3.27).
- If 0xtikaa picks MKV, only P3.10 and P3.11 change.

Q4, snapshot memory strategy.
- What the code assumes now: `DvrBuffer::snapshot` returns an owned `DvrClip { packets: Vec<Packet> }`, and the specs depend on that. `Recorder::snapshot` copies while holding the recorder mutex. Encoder and audio threads wait for the whole copy: about 150 MB for 60 s at maximum bitrate, about 750 MB for 5 min. RAM transiently doubles.
- Recommendation: keep the copy for v0.1 and measure it (P3.17 logs the lock-hold time; P3.27 records it).
- Why:
  - Segments shared by reference need Arc'd fixed-size segments. A dump that pins segments forces the ring to allocate replacements, so it costs RAM anyway.
  - It would also change the spec'd DvrClip API.
  - The copy is simple, already spec'd, and only rarely slow.
- Revisit in Phase 4 (together with Q6, resize) if a 300 s snapshot holds the lock for more than about 20 ms, or if audio glitches during dumps. Until then, Phase 2 should give WASAPI a generous buffer duration (at least 200 ms) so a long lock hold does not cause audio glitches.
- Also note that the 1 GiB RAM ceiling covers the ring, not ring plus snapshot.

Q5, DVR and session recording at the same time?
- What the code assumes now: both. `Recorder::push` already writes the DvrBuffer and then the Tee, and the Tee specs exist.
- Recommendation: allow them together, with one recording slot (manual or session) at a time.
- Why:
  - Making them exclusive saves nothing. Manual recording goes through the same Tee and spool path, and the DVR keeps buffering for free. The only extra cost is the 32 MiB spool.
  - One slot keeps the actor simple. ToggleRecording stops whatever is recording.
- The session auto-trigger depends on Phase 4 pieces (`ProfileSet::resolve`, a process-exit event), so the trigger moved to Phase 4 (P4.7).

Other open questions this area touches:
- Q6 (Phase 4): `DvrBuffer::resize` is implemented in P3.4 by snapshotting and re-pushing. The writer pause is simply the recorder lock. A resize must re-run page-locking (P3.25).
- Q8 (HDR): hvcC and av1C hardcode 8-bit 4:2:0 for NV12. Revisit them if a P010 path ever appears.

Decision process: CLAUDE.md requires asking before deciding an open question. (Superseded: 0xtikaa settled Q3–Q5 in planning as D18–D20. P3.0 and P3.26 were removed; the session trigger lives in P4.7.)

### P3.1 · zc-core::ring::PacketRing, an allocation-free FIFO of packets in one pre-allocated byte ring

Size **M** · no hardware needed · depends on nothing

**Files:**
- `crates/zc-core/src/ring.rs`
- `crates/zc-core/src/lib.rs`

**Reuse:**
- zc_core::media::{PacketMeta, PacketRef} (crates/zc-core/src/media.rs)

**Steps**

This type is the building block for the DVR buffer (one ring per track) and for the recording spool in P3.21. Write it once.
1. Create crates/zc-core/src/ring.rs. In lib.rs, add `pub mod ring;` and a row to the module table: allocation-free packet FIFO, used by the DVR buffer and the recording spool (DESIGN section 4 and section 5).
2. Types:
   - `#[derive(Clone, Copy)] struct Entry { meta: PacketMeta, start: usize, len: usize }`
   - `pub struct PacketRing { bytes: Box<[u8]>, entries: VecDeque<Entry>, max_packets: usize, head: usize, used: usize }`. `head` is the start of the oldest packet. `used` is the payload bytes stored.
3. `pub fn new(capacity_bytes: usize, max_packets: usize) -> Self`. Allocate with `vec![0; capacity_bytes].into_boxed_slice()` (calloc, so pages are committed lazily) and `VecDeque::with_capacity(max_packets)`. Document that this is the only allocation.
4. Accessors: `capacity()` (bytes), `used()`, `len()`, `is_empty()`, `front()` and `back()` returning `Option<PacketMeta>`.
5. `has_room_for(len)`: `capacity > 0 && used + len <= capacity && entries.len() < max_packets`. Track `max_packets` yourself, because VecDeque may reserve more than asked.
6. `#[must_use] pub fn push(&mut self, p: PacketRef<'_>) -> bool`. If there is no room, return false and store nothing.
   - Otherwise compute `tail = (head + used) % capacity`.
   - Copy in at most two pieces: `first = len.min(capacity - tail)`; `bytes[tail..tail+first] = data[..first]`; `bytes[..len-first] = data[first..]`.
   - Then `entries.push_back(Entry { meta, start: tail, len })` and `used += len`.
7. `pop_front() -> Option<PacketMeta>`: set `head = (start + len) % capacity` and `used -= len`. If the ring is now empty, reset `head = 0`.
8. `pop_front_into(&mut self, out: &mut Vec<u8>) -> Option<PacketMeta>`: `out.clear()`, extend it with both pieces, then pop. The spool's IO thread uses this.
9. `iter(&self) -> impl DoubleEndedIterator<Item = (PacketMeta, [&[u8]; 2])> + '_`. Map each entry to its one or two slices: `a = len.min(capacity - start)`.
10. `clear()`.
11. Write `impl fmt::Debug` by hand, showing capacity, used and len. Never print the bytes: a ring can be 750 MB, and DvrBuffer derives Debug.
12. No `format!`, tracing or allocation in any method except `new` and `pop_front_into`'s `out`.
13. Add two plain #[test]s:
   - `ring_wraps_packets_around_the_end`: capacity 10. Push 4 bytes of 'a' and 4 of 'b', pop once, then push 4 of 'c'. The 'c' packet wraps; iter must yield b, then c split [2, 2], and the reassembled bytes must equal the input.
   - `ring_refuses_what_does_not_fit`: full by bytes, full by count, and capacity 0 must all return false and store nothing. Capacity 0 must not panic on `% 0`.

**Verify**

cargo test -p zc-core ring_; cargo clippy --workspace --all-targets -- -D warnings; cargo fmt --all

**Steps**

1. Fields, replacing the 'your storage goes here' comment:
   - `config`
   - `video: PacketRing`
   - `audio: [PacketRing; 2]` (index = `track.index() - 1`)
   - `gops: usize`
   - `current_gop_bytes: usize`
   - `newest_video_end: Hns`
   - `skip_until_keyframe: bool`
   The per-frame index, with keyframe entries marking GOP starts, *is* the GOP index. Say so in the module doc's rule 2.
2. Constants, each with a short `ponytail:` note on its ceiling:
   - `VIDEO_BYTES_PER_ENTRY = 1024`. Frames average at least 1 KiB at 2 Mbps and 240 fps.
   - `AUDIO_BYTES_PER_ENTRY = 128`. MF's AAC encoder is CBR, so frames are at least 170 B even at 64 kbps.
   - `MIN_ENTRIES = 1024`.
   `new()` builds each ring with `PacketRing::new(bytes, (bytes / PER_ENTRY).max(MIN_ENTRIES))` and sets `skip_until_keyframe = true`. Do not add fields to DvrConfig: the specs construct it with struct literals.
3. `push`:
   - If `self.video.capacity() == 0`, return `Ok(PushOutcome::Discarded)`. The engine passes zero sizes when DVR is turned off in settings.
   - Otherwise dispatch on `meta.track`.
4. `push_video`, in order:
   a. If keyframe: `skip_until_keyframe = false; current_gop_bytes = 0`. Else if `skip_until_keyframe`: return Discarded.
   b. `gop_bytes = current_gop_bytes + len`. If `gop_bytes > video.capacity()`: set skip_until_keyframe and return `Err(DvrError::GopTooLarge { bytes: gop_bytes, capacity })`. The rest of that GOP is Discarded, so the recorder counts one error per GOP.
   c. Evict: `while !video.has_room_for(len)`, compute `evictable = if keyframe { gops } else { gops - 1 }`. If evictable is 0 (the index is full inside one GOP), skip until the next keyframe and return GopTooLarge. Otherwise call `evict_oldest_gop()`.
   d. Push (`debug_assert!` that it succeeded). On a keyframe, `gops += 1`. Set `current_gop_bytes = gop_bytes` and `newest_video_end = meta.end()`.
   e. `trim_audio()`, then return Stored.
5. `evict_oldest_gop()`: pop the front, which is always a keyframe, then pop while `front()` is not a keyframe. Then `gops -= 1`.
6. `trim_audio()`: for each audio ring, pop while `front.pts < oldest video pts`, or pop everything if no video is retained. This is 'audio follows video'.
7. `push_audio`:
   - With no video retained, or `pts < oldest_pts()`: Discarded.
   - Otherwise `while !ring.has_room_for(len) { if ring.pop_front().is_none() { return Ok(Discarded) } }`, then push and return Stored. When the audio ring is full on its own, the oldest audio is dropped.
8. Accessors:
   - `gop_count() = gops`
   - `oldest_pts() = video.front().map(|m| m.pts)`
   - `buffered() = oldest.map_or(ZERO, |o| newest_video_end - o)`
   - `used_bytes(track)` = that ring's `used()`, which is payload bytes as the specs expect.
9. `clear()`: clear every ring, zero the counters and `newest_video_end`, and set `skip_until_keyframe = true`.
10. Hot-path rule: nothing in push may allocate, format or log. `DvrError` is Copy-like, so returning it does not allocate.
11. Remove the #[ignore] from the listed specs, including tests/dvr_no_alloc.rs line 61. Leave the snapshot and resize specs for P3.4.

**Verify**

cargo test -p zc-core dvr_; cargo test -p zc-core --test dvr_no_alloc; cargo test -p zc-core -- --ignored (the specs above no longer appear); cargo clippy --workspace --all-targets -- -D warnings; cargo fmt --all

   - Header byte: obu_type = `(b >> 3) & 0xF`, extension flag = `b & 0x4`, has_size = `b & 0x2`. If the extension flag is set, skip one extension byte.
   - If has_size, read the size as leb128; otherwise the OBU runs to the end of the buffer.
   - `pub fn av1_obus(data) -> impl Iterator<Item = (u8, &[u8])>` yields `(type, whole OBU bytes)`.
2. `av1_sequence_header(data) -> Option<&[u8]>`: the first OBU of type 1.
3. A small `BitReader { data, pos }` with `bits(n) -> Option<u32>` and `uvlc()`.
4. `pub fn av1c(seq_obu: &[u8]) -> Vec<u8>`. Parse from the OBU payload:
   - seq_profile (3), still_picture (1), reduced_still_picture_header (1).
   - If reduced: seq_level_idx_0 is the next 5 bits and the tier is 0.
   - Else:
     - timing_info_present (1). If set, skip num_units_in_display_tick (32) and time_scale (32); then equal_picture_interval (1), and if that is set, a uvlc. Then read decoder_model_info_present (1); if set, skip 5 + 32 + 5 + 5 bits.
     - initial_display_delay_present (1), operating_points_cnt_minus_1 (5), operating_point_idc[0] (12), seq_level_idx[0] (5). seq_tier_0 is 1 bit if the level is above 7, else 0.
   - Record: `[0x81, (seq_profile << 5) | level, (tier << 7) | 0b0000_1100, 0x00]`, then the whole sequence-header OBU as configOBUs.
   - The color bits are hardcoded to 8-bit 4:2:0 for NV12 (`ponytail:` revisit with Q8 HDR).
   - If there is no sequence header, return `[0x81, 0, 0x0C, 0]`.
5. fmp4.rs: Codec::Av1 gets sample entry `av01` with an `av1C` child. Sample data is every OBU except temporal delimiters (type 2), which AV1-in-ISOBMFF says to drop. The OBUs must keep their size fields.
6. Test `av1c_from_a_sequence_header`:
   - Hand-pack a header with seq_profile 0, reduced 0, no timing info, no initial delay, 0 extra operating points, op_idc 0, level 8, tier 0.
   - Expect record[1] == 0x08 and record[2] == 0x0C.

**Verify**

### P3.19a · DurableFile: sync recordings to disk at every fragment (D18 robustness)

Size **S** · no hardware needed · depends on P3.6, P3.7, P3.11, P3.19

**Files:**
- `crates/zc-mux/src/durable.rs`
- `crates/zc-mux/src/lib.rs`
- `crates/zc-engine/src/output.rs`

**Reuse:**
- zc_mux::chunked::ChunkedWriter (flush forwards the partial chunk)
- PacedWriter (P3.7)
- output::open_writer (P3.19)

**Steps**

Why: `std::fs::File::flush` is a no-op. Bytes sit in the OS cache until Windows decides to write them, so a power loss loses them. `File::sync_data` calls `FlushFileBuffers` on Windows (https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers). This is pure std, so zc-mux stays free of the windows crate.
1. `crates/zc-mux/src/durable.rs`: `pub struct DurableFile { file: File, sync_on_flush: bool }`.
   - `pub fn recording(file: File) -> Self` syncs on every flush.
   - `pub fn dump(file: File) -> Self` never syncs on flush.
   - `pub fn sync(&self) -> io::Result<()>` calls `sync_all`.
   - `impl Write`: `write` forwards; `flush` calls `self.file.sync_data()` when `sync_on_flush`.
   Doc-comment the why and link the MS page.
2. The stack is container → `ChunkedWriter` → `PacedWriter` → `DurableFile`. With the P3.11 amendment, every fragment calls `flush` down the chain, so each GOP reaches the disk.
   - Fragments are about 6 MB at 50 Mbps, below the 8–16 MiB chunk, so per-fragment flushes replace chunk-sized writes for recordings. That's fine: recordings stream at bitrate.
   - HDD pacing still applies to dumps.
3. `output::open_writer` takes `durability: Durability { PerFragment, AtFinish }`. `write_clip` (DVR dumps) uses `AtFinish` and calls `sync()` after `finish()`; 300 fsyncs on an HDD would add 3–6 s to a 5-minute dump. Recordings and crash-rescue dumps use `PerFragment`.
4. Test (zc-mux, temp file): write 3 synthetic GOPs through `Fmp4Writer` over `ChunkedWriter<DurableFile::recording>` with a 16 MiB chunk. After the second fragment is cut (third keyframe pushed), `fs::metadata(path).len()` equals the bytes produced so far. That proves the partial chunk was forwarded rather than held in RAM.

   b. While skipping: a video keyframe clears the flag; anything else returns `Ok(())` (silently dropped).
   c. If `!ring.push(p)`: set `skip_until_keyframe = true` and return `Err(SinkError::Full)`. Dropping until the next IDR keeps the file decodable.
   d. Unlock, then `ready.notify_one()`.
   No allocation, no tracing.
3. `impl Drop for SpoolWriter`: set `closed = true` and notify. Detaching the writer from the Tee and dropping it ends the recording.
4. `SpoolReader::next(&self, buf: &mut Vec<u8>) -> Option<PacketMeta>`: loop on `ring.pop_front_into(buf)`. If empty and closed, return None; otherwise `ready.wait`. The lock is held only for the memcpy, never across I/O.
5. `pub(crate) fn drain(reader: SpoolReader, mut out: Box<dyn ContainerWriter>) -> io::Result<Hns>`:
   - For each packet, `out.write_packet(PacketRef { meta, data: &buf })?`.
   - Track the first video pts and the last video end.
   - Then `out.finish()?` and return the duration.
6. Tests, using a fake ContainerWriter that records metas and a finished flag behind `Arc<Mutex<..>>`:
   - `spool_starts_at_a_keyframe_and_drains_in_order`: write SyntheticStream frames 10..130, drop the writer, drain. The first packet is frame 60, there are 70 frames, and finish was called.
   - `spool_skips_to_the_next_keyframe_when_full`: a small capacity with no draining gives Err(Full). After draining, the recorded sequence never resumes mid-GOP.
7. Do not add a no-alloc test: the global allocator would apply to the whole lib test binary. `PacketRing::push` is already covered through `dvr_push_never_allocates`.

**Steps**

D18: a crash may leave a recording that ends mid-fragment. Repair it at startup so the user loses at most about 1 s.
1. `crates/zc-mux/src/repair.rs`: `pub fn last_complete_fragment_end<R: Read + Seek>(r: &mut R) -> io::Result<Option<u64>>`.

   - On `Unrecoverable`, leave the file untouched. Never delete unverified (D15 spirit).
3. App: in `ZeroClipApp::new`, spawn a std thread that scans `output_dir()` for `*.partial`, calls `repair_partial` on each, and sends the results to the UI. 4. Tests in repair.rs, building files in memory with `Fmp4Writer` over a `Cursor<Vec<u8>>` from `SyntheticStream`:

   - truncated mid-`mdat` of fragment 3: end of fragment 2;

### P3.25 · Page-lock the DVR buffer (VirtualLock after raising the working set)

Size **M** · **hardware check: 0xtikaa** · depends on P3.18

**Files:**

**Reuse:**
- zc_win::error::WinResultExt (crates/zc-win/src/error.rs)
- PacketRing (P3.1)
- Recorder::lock (recorder.rs)

**Steps**

1. Expose the memory:
   - ring.rs: `pub fn memory(&self) -> &[u8] { &self.bytes }`.
   - dvr.rs: `pub fn memory(&self) -> [&[u8]; 3]` returning the video and both audio rings. Doc: for page-locking (DESIGN section 4); the addresses are stable until `resize`.
2. ports.rs: `pub type LockMemory = fn(&[u8]) -> Result<(), SourceError>;`.
3. recorder.rs: `pub fn lock_memory(&self, lock: LockMemory) -> Result<usize, SourceError>`. Hold the state lock, call `lock(region)?` for each `dvr.memory()` region, and return the total bytes.
4. zc-win: add the feature "Win32_System_Memory" for VirtualLock. Win32_System_Threading, which provides GetCurrentProcess, GetProcessWorkingSetSize and SetProcessWorkingSetSize, is already declared. Add `pub mod memory;` and a doc bullet to lib.rs.
5. Write `pub fn lock(region: &[u8]) -> Result<(), SourceError>` in memory.rs:
   - Return `Ok(())` for an empty region.
   - `let process = GetCurrentProcess();`. It is a pseudo-handle and needs no close.
   - `GetProcessWorkingSetSize(process, &raw mut min, &raw mut max).context(..)?`.
   - `extra = region.len() + 2 * 4096`, because a region spans at most two partial pages.
   - `SetProcessWorkingSetSize(process, min.saturating_add(extra), max.saturating_add(extra)).context(..)?`. VirtualLock fails past the minimum working set, which defaults to about 200 KB.
   - `VirtualLock(region.as_ptr().cast(), region.len()).context("VirtualLock")`.
   - SAFETY comments: the region is a live allocation for the whole call, and VirtualLock only pins pages and never writes.
   - Doc: explain the working-set quota and link the Microsoft Learn pages for VirtualLock and SetProcessWorkingSetSize.
   - No unlock: freeing a large allocation (which HeapAlloc serves with VirtualAlloc) releases the lock. Phase 4's resize must re-lock the new rings; note that on the ROADMAP Phase 4 line.
6. Add `pub lock_memory: Option<LockMemory>` to zc_engine::Ports and its Debug impl. After the actor creates the Recorder, on the engine thread:
   - `match recorder.lock_memory(lock)`. On Ok, `tracing::info!(mib = bytes >> 20, "DVR buffer page-locked")`.
   - On Err, emit Warning("Couldn't page-lock the DVR buffer ({e}). Clipping still works, but Windows may page it out under memory pressure.").
7. In src/wiring.rs, set `lock_memory: Some(zc_win::memory::lock)`.
8. Test in memory.rs, `locks_a_small_buffer`: `let buf = vec![0u8; 1 << 20]; assert!(lock(&buf).is_ok());`. Ordinary users hold SeIncreaseWorkingSetPrivilege, so it runs on CI.

**Verify**
